## Step 1: investigation

### (a) Does the 2026-10-08 Communications tab already show texts?

Partly. `loWsCommunications` (on both the LO Workspace lead page and the loan page) has an **SMS** subtab, but it reads **Task** rows only: RingCentral `InteractionType__c = 'Sms'` and manual "Text" logs, for the borrower. It never reads `TwilioSF__Message__c`, and it has nothing for agents.

So no duplicate tab was added. The Communications tab is **extended** with a 4th subtab, **Texts** (Calls / SMS / Emails / Texts). The realtor page reuses the same component in a new `texts-only` mode.

### (b) What creates TwilioSF__Message__c (full flow + Apex retrieve, 2026-10-09)

Every send goes through the invocable `TwilioSF__TwilioSendSMS`. Its `recordId` input becomes `TwilioSF__SF_Parent_Record_Id__c`: the sending context is already stored on every message. No Apex inserts messages directly.

### (c) Attribution design (built, no flow edits needed)

New fields on `TwilioSF__Message__c`. Custom fields and triggers on the managed object are allowed; this was confirmed by the check-only deploy.
- `LoWs_Transaction__c` / `LoWs_Lead__c`: origin.
- `LoWs_Phone_Key__c`: last 10 digits of the other party's number. It is an External Id, so it is indexed (154k rows).
- `External_LO__c` (label "Workspace LO").

Trigger `ExternalLoStampTwilioMessage` → `LoWsTextsService.stamp` (before insert/update). Origin is set **once**.
- **Outbound:** a parent that is a Transaction gives `LoWs_Transaction__c`, and a parent that is a Lead gives `LoWs_Lead__c`. With no parent at all, `TwilioSF__Lead__c` is used. An Account or Contact parent gives nothing: birthdays, anniversaries, realtor referral thank-yous and event invites name no loan, so they would be ambiguous.
- **Inbound:** copies the origin of the **most recent outbound text to the same phone key within 30 days**, even if that one is unstamped. This is stricter than "most recent *stamped* outbound": if another LO texted the realtor last, the reply stays with that thread and never reaches this LO (Q27).
- **Workspace LO:** `ExternalLoStampService` rules on the origin (Transaction: Loan_Officer__c > Loan_Partner__c > Owner; Lead: Owner > Loan_Partner__c). TwilioSF__Message__c was added to its `PARENT_FIELDS`, so a lead or loan reassignment restamps the texts (existing queueable).
- An origin filled later by EDGE (blank parent → borrower's active loan) is accepted. EDGE's Lead→Transaction rewrite does not move an origin that is already set.

**Coverage, last 30 days** (1,683 messages; the agent texts are the ones whose number matches one of the 5,745 Realtor Person Accounts):

| | total | attributable to a loan/lead |
|---|---|---|
| Outbound to agents | 456 | **380 (83%)** — 312 lead, 68 loan |
| Inbound from agents | 68 | **58 (85%)** |
| All outbound | 1,509 | 578 (38%). The remainder are birthday/anniversary texts (712) and staff notifications. |
| All inbound | 174 | 134 (77%) |

The 76 agent sends with no loan context are 50 referral thank-yous (realtor Account parent), 14 staff notifications sent to a number that is also a realtor's, and about 12 manual sends with no parent.
Today only the pilot is in the External_Loan_Officer role, so ~0 rows would actually get `External_LO__c`; the 83%/85% figures show what each LO's own texts will get.

## Step 2: what was built

**Access path: Apex SYSTEM_MODE.**
- LOs have **no** object access to TwilioSF__Message__c (checked: neither the profile nor the PSG grants it). Nothing was added, so no permission set changes and no PSG recalculation.
- Every read filters `External_LO__c = me` for `External_LO` holders.
- Restriction rule `TwilioSF_Message_External_LO` (`$Permission.External_LO = true` / `External_LO__c = $User.Id`) is deployed as a guard. If an LO is ever given a Twilio seat, its permission set would grant Read on a Public R/W object. The validation shows that restriction rules accept this managed object.

## Open questions (owner decisions)

1. **Past-client birthday/anniversary texts** (Account parent, 712/month). Should an LO see them for past clients they own? Not built, because realtor Accounts can be owned by an LO too, which would surface referral thank-yous about other LOs' leads.
2. **Recent log shows every stamped reply**, borrower or agent. Telling an agent from a borrower needs a realtor-phone lookup. Do we want agent-only?
3. **SMS vs Texts.** Two subtabs (RingCentral SMS and Twilio Texts) could be merged into one thread later.
4. **Thread window** is 30 days. Is that right?

## Risks

- First deploy of a trigger on a managed object. Package upgrades do not touch subscriber triggers, but test inserts fire the package's own triggers and flows (the validation exercised them).
- EDGE's heuristic can attribute a no-parent borrower text to the borrower's most recent active loan (accepted; it only applies to borrower numbers).
- The backfill updates ~5.3k rows (LastModified changes; EDGE does not re-fire).
