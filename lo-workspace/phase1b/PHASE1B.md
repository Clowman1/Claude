# Phase 1b: sharing-bypass fixes (External Loan Officer)

Status: **drafted and validated, NOT deployed.** Dry-run `0AfQi000001TjVpKAK` (2026-10-01) succeeded: 198 tests, 0 failures, no coverage warnings.

Sources were retrieved fresh from `Production` (2026-09-30) and re-checked on 2026-10-01. None of the touched classes changed in prod in between. Unchanged retrieved copies are parked in `reference-unchanged/` so they stay out of the deploy. `force-app/` holds only the files that change.

## Approach

One new helper, `RecordAccessGuard` (without sharing, about 100 lines). Each entry point that takes a record Id from the browser calls it **before** doing any without-sharing work:

- **Internal users:** `UserRecordAccess` (HasReadAccess or HasEditAccess) for the running user.
- **Partner Workspace community users** (UserType not Standard): the same ownership rule the portal's own detail queries use. A Lead counts if `OwnerId` is the user. A Transaction counts if `Loan_Officer__c` or `OwnerId` is the user. Their license has no Lead object access, so `UserRecordAccess` cannot be trusted for them.
- **Guest users:** always refused. No guest page reaches a guarded method. Several guest profiles do hold these classes through `Condition_Files_Permissions` (see the decisions list).
- Errors come back as `AuraHandledException('You do not have access to this record.')`, with `setMessage` so callers that rewrap keep the text.

No class sharing keyword was changed. Every class keeps its existing route for guest and portal callers, and no USER_MODE was added to any guest path. A plain `with sharing` change was rejected for three reasons. `Call_Insight__c` is **Private externally**, so the Partner Workspace Calls tab would go blank. Loan Officers have Read-only Transaction access. And `AppraisalOrderController` is held by a guest profile.

The Phase 2 Restriction Rules do **not** protect without-sharing Apex. These guards are what close those paths.

### RecordAccessGuardTest (new)

It creates two users exactly as production sets them up: profile `External Loan Officer Profile`, role `External_Loan_Officer`, permission set `External_LO_Access`, and permission set group `External_Loan_Officer`. The group carries the Condition__c, request and file permissions, without which the legitimate path cannot run.

- **loA** owns the Lead and Account and holds a Manual **Read** share on an admin-owned Transaction. That is what `LoanOfficerRecordSharingService` gives a real LO.
- **loB** owns nothing.

The tests prove that loA (and the admin, for the Transaction writes) still works, and that loB is refused at every guarded entry point.

It works with the live Phase 2 automation:

- `ExternalLoStamp*` triggers stamp `External_LO__c` on insert, and the test relies on that (Call_Insight and the request become loA's).
- Two records are re-stamped to loB with a direct update, which sticks because the trigger recomputes only when the parent changes. These give loB a record it can read under the restriction rules, so the guard itself (not a restriction rule) is what refuses loB.
- The class is `without sharing` so that no-keyword controllers run as they do from Aura.
- The portal ownership branch is exercised with a `@TestVisible userType` override.

## Needs a human decision / not safely fixable here

1. **AppraisalOrderController: no change made.** Its record methods are already gated by LoanRepository. Adding `with sharing` would hide `ValueLink_Log__c` (Private externally) from the guest and community profiles that hold the class. `downloadSingleFile(fileId)` still fetches any ValueLink document by its ValueLink Id with no loan check. Fixing that needs a `loanId` parameter plus an Aura change, so decide whether External LOs need the Appraisal tab at all.
2. **Transaction writes are gated on read, not edit** (TransactionNotesForm `saveNotes`/`createNote`, SubmissionQualityChecklist `saveChecklistAnswers`). This keeps today's legitimate users. In practice a read-share LO's save is already rejected by Transaction automation (`INSUFFICIENT_ACCESS_ON_CROSS_REFERENCE_ENTITY`, seen in testing). Decide whether these should be edit-only (processors).
3. **`Condition_Files_Permissions` is assigned to 9 guest site users**, including the Integrations, Lead Intake, Closing Portal, Borrower Portal and Title sites. It grants DocumentViewerController, ConditionReviewQueueController, DocumentController and ConditionCommentController to unauthenticated users. The guard now refuses guests on the guarded methods, but the other with-sharing methods remain callable. Recommend removing the permission set from every guest user (verify Borrower Portal v2 comments first).
4. **Guest sharing rules:** about 176k Lead and 54k Transaction rows are shared Read to guest users (GuestRule). Any with-sharing Apex a guest can call sees them. The portals use SYSTEM_MODE, so these rules may be unnecessary. Needs review.
5. **Remove `BorrowerDocumentPortalController.markProcessorCommentUnreadForBorrower`** once this deploy is live. It is left in place because it is a guest class and nothing calls it after this change.
6. **ConditionReviewService** now checks that a document is *readable*, not that it is linked to the condition. One existing test moves a document after a rejection has already unlinked it, so a strict link check would break real sequences. Edge case left open: approving the review status of a readable file that is not on the condition.
7. **Partner Workspace `handleInternalFileUpload`:** `getLeadOrThrow` uses USER_MODE and community users have no Lead CRUD, so the portal upload may already be failing. This predates Phase 1b and needs a check as the outside LO test user.
8. **LeadNotesForm saves now need Lead Edit.** The 118 read-only rule shares (Nickley/Lawrence groups) can still view but not save from the modal. Confirm that is intended.
9. Not reviewed in depth: the other `DocumentController` methods (with sharing, but `updateConditionFileDetails` queries ContentVersion by document Id with no access check) and `ConditionReviewQueueController`'s read methods.
